# Local drafts and history

The production Studio composes these modules through `application.js` and `studio-lifecycle.js`. Draft persistence is browser-only; no local-save event publishes. The Dashboard reads the authenticated published catalog. See [Studio](customization-studio.md) and [publication](profile-publication.md).

## Responsibilities

| Module | Responsibility |
| --- | --- |
| static/js/draft-schema.js | Generated P3 draft/profile JSON Schemas and limits; no handwritten second schema |
| static/js/draft-contract.js | Strict browser validation, semantic geometry/identity checks, defensive copies, access-context assertions and non-secret random IDs |
| static/js/draft-publications.js | P5 configuration-only operation journal in the same database |
| static/js/draft-store.js | Native IndexedDB transactions, optimistic compare-and-swap, context-scoped erasure and revocation |
| static/js/edit-history.js | Session-only bounded snapshots, undo/redo and grouped gestures |
| static/js/draft-session.js | Explicit new/resume lifecycle, debounced local persistence, coherent preview, keep/discard/logout policies and publication handoff |
| scripts/generate_profile_schema.py | Deterministic generation and --check mode from existing P3 models |

Load order is schema, validator, history, publication journal, store and session before the Studio composition. Never wire local draft changes to a server autosave path.

Regenerate with python scripts/generate_profile_schema.py. The Python contract test checks generated bytes and the shared semantic corpus; Node runs the same corpus against the browser validator. Generated JSON Schema does not encode every cross-field rule: identity uniqueness, geometry bounds, printable labels and encoded sizes are also checked explicitly. Update both semantic validation and the corpus if P3 evolves.

## Three separate states

1. Published: a validated profile supplied by the authenticated production host; never mutated by this library.
2. Draft: ccs-dashboard-draft version 1, exactly as defined in [P3](profile-contracts.md): storeId/profileId/draftId, baseRevision/localRevision, updatedAt, name and full configuration. No secrets, live data or history fields are allowed.
3. Preview: a fresh copy of draft name/configuration. Real or synthetic widget data must remain a separate transient renderer input. Passing GSI, socket or diagnostics fields to draft validation fails; the library has no API accepting those packets.

All state crossings validate and copy. Mutating a returned preview or a caller's original profile cannot mutate the other states. History snapshots contain configuration content only. There is no reference shared with a published dashboard object.

## IndexedDB and access isolation

Database ccs-local-drafts now uses database version 2, with contexts, drafts and the P5 publications journal. The upgrade from version 1 only adds that store and preserves existing drafts. These database/envelope versions are separate from the P3 draft version.

The authenticated host obtains a stable installation generation (storeId) and a stable, opaque, non-secret access-realm ID (accessId) after actual authentication. Both are 32 lowercase hexadecimal characters. accessId must be shared by tabs in the same authorized realm and stable across normal reloads. The maintainer approved P5 deriving it only from the public storeId; a PIN change alone does not rotate it. Do not derive it from the PIN, a PIN hash, GSI token or socket/session credential. Do not create a fresh accessId per tab or it would prevent cross-tab detection and context-wide logout cleanup.

The authenticated catalog provides this context; `CCSDraftContract.access({storeId, accessId, authenticated: true})` is a trusted host assertion, not authentication. The production transport must finish real PIN authentication before constructing it.

Context metadata is keyed by [storeId, accessId]. Drafts are keyed by [storeId, accessId, draftVersion, profileId], with writeId, createdAt (first committed local creation), and the validated draft. updatedAt is the last local edit timestamp in Unix milliseconds. No authentication state, PIN, token, match packet, raw socket frame or diagnostic log is persisted. A single configured shared-PIN installation is not a multi-user account system.

IndexedDB is origin-isolated, not an encrypted vault. Other authorized same-origin scripts, browser-profile access, extensions or a compromised device may read configuration. Clearing browser data or browser eviction can remove drafts. HTTP/LAN remains unencrypted as documented by CCS. Random IDs use getRandomValues, including on HTTP origins where randomUUID is not available; they are identifiers, never authentication credentials.

## Transactions and multiple tabs

Every save reads the previous record and compares its random writeId within the same read/write transaction. A create requires absence; an update also requires the same draftId, baseRevision and localRevision. A successful save increments localRevision and assigns a fresh writeId. This detects two editors, deletion/recreation and stale local revisions without silent last-writer-wins behavior.

Different profiles have different keys. Two editors of one profile may retain their own in-memory edits, but the stale writer receives local_conflict. Detection happens on the next read/write or explicit inspection; there is no realtime collaboration or continuous cross-tab broadcasting. The UI must offer a deliberate decision rather than retrying with another tab's token automatically.

The save promise resolves only on transaction complete, not request success. Aborted writes retain the previously committed record. The session serializes saves, coalesces ordinary changes for 200 ms, suppresses no-op changes, and drains a newer coherent state after an in-flight write. An error retains pending in-memory work and the last committed draft; it never falls back to server publication.

## Lifecycle and error states

CCSDraftSession.inspect({store, profileId, published}) performs a read without mutation and returns none, available, incompatible, corrupt, profile_deleted, remote_newer, revision_mismatch or storage_unavailable (with a stable underlying code). Callers must supply the latest authenticated published revision. start requires an explicit choice: new only when no draft exists, resume only when a valid draft matches the profile/base revision. It never rebases a stale draft automatically.

An incompatible/corrupt record is retained. Explicit store.remove(profileId, token) discards a known record with compare-and-swap; a confirmed context purge can remove malformed records that cannot supply a usable token. There is no automatic cleanup or migration. A target database version newer than supported is refused rather than downgraded.

Stable error/status codes are translation keys for FR/EN presentation, not English UI strings. Important codes include quota_exceeded, transaction_aborted, storage_unavailable, storage_blocked, database_incompatible, context_revoked, local_conflict and revision_limit. An aborted deletion leaves the draft and access context intact. The UI must show pending/error states and permit explicit retry or preservation in memory; it must not claim the work is saved.

### Keep, discard, disconnect and logout

- keepAndLeave() freezes edits, flushes the latest state, verifies the stored token and returns kept only after confirmed local persistence. It performs no network action. Failure leaves the session open with its work intact.
- discard() stops scheduled writes, waits for an in-flight save to settle, and removes only the record matching this session's token. A conflict or deletion failure leaves the session open; it cannot erase another tab's newer record.
- dispose() stops session activity without deleting the committed draft. It is not a claim that pending work was saved. No network-loss/reconnect handler clears drafts.
- logout({store, confirmed: false}) cancels without changes. confirmed: true atomically deletes all draft and publication-journal versions for this installation/access realm and increments its persistent local epoch. Only after success should the host invalidate authentication and dispose in-memory editing sessions. If deletion fails, logout must not claim completion.
- Other open handles retain the old epoch and cannot write drafts back after confirmed cleanup. A pending write ordered before cleanup is deleted; a write ordered after cleanup fails. Other installations/access realms remain intact, including if draft metadata is corrupt: erasure uses the primary-key scope.

Closing/reloading normally retains completed transactions. A 200 ms debounce, an active gesture or an in-flight transaction may be interrupted by abrupt browser/process termination. Browser unload handlers cannot guarantee an awaited IndexedDB flush. The Studio warns about unconfirmed work and awaits keepAndLeave for controlled Studio navigation. Transaction completion is browser confirmation, not a hardware fsync or an unlimited retention guarantee.

## Undo/redo and gestures

History is independent of the server and is never stored in IndexedDB. It holds at most 50 undo/redo snapshots and 2 MiB of UTF-8 serialized history content combined, dropping oldest entries first. Current content and an active gesture baseline are additional bounded configurations. This is a deterministic content budget, not a measurement or ceiling for total JavaScript heap usage.

Fifty operations provide useful recovery while bounding retention of large layouts. Cached per-snapshot byte lengths avoid repeatedly encoding all retained history during each edit. New edits after undo clear redo; identical no-op edits do not add entries. Reset starts a fresh history.

Use beginGesture(), previewGesture(next), then endGesture() for a drag/resize. Intermediate states update only the independent preview. End creates one history operation and schedules one coherent local save; cancelGesture restores the initial state. Explicit flush/exit during a gesture is refused until it is committed/cancelled. Other configuration changes use edit(next); undo/redo schedule local persistence and never change the published profile.

## Verification and reproducible measurements

Run node tests/js/test_drafts.js and python tests/browser/test_drafts.py --browser chromium (also firefox/webkit in CI). The native-browser test uses temporary persistent browser profiles, real IndexedDB and a synthetic server. It checks reload/full-process reopen, two-tab CAS, different profiles/contexts, quota/transaction/delete failures, stale/deleted profiles, corruption/future formats, logout during a write, schema-independent cleanup, HTTP origins and absence of secrets/server saves. Fault adapters retain real native transactions; they inject failures before transaction completion.

For local timing evidence use --output ../draft-evidence. The same 1280x900, en-US/UTC scenario uses 60 widgets, 100 rapid edits, 100 gesture previews and seven restores. Raw timings accompany write counts and retained history bytes. Timings include validation/copying and browser storage overhead; there is no arbitrary CI latency gate or claim of a rendering speedup. Select browser/widget/theme regressions for the affected behavior.

## P8 composition

The integrated [Customization Studio](customization-studio.md) now composes these modules, including explicitly local baseRevision-0 creations, context-scoped draft enumeration and optional pristine deferred baselines. Default existing session callers keep their behavior. The production lifecycle supplies creation, resume, discard, conflict and logout UI. Publication snapshots/leases hand the exact persisted draft to the existing publication controller; saving locally alone never publishes.
